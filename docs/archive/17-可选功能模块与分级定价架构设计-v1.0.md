# 17 · 可选功能模块与分级定价 · 系统架构设计

版本：v1.0.0
日期：2026-11-10
状态：**设计稿，待评审**。本文不含任何实现改动；评审通过后再进入开发。
范围：把「邮件分享（预览/编辑链接外发）」「AD 用户认证」「文件密级管理」三项能力改造为可按租户、按需启用的可选模块，并支撑分级定价。

---

## 1. 结论摘要

采用**五层授权模型 + 单一执行点**，而不是在现有 `feature_flag` 上继续加开关：

```
L0 全局熔断（运维止血，非商务）
L1 能力目录（代码拥有：编码、依赖、关闭语义）
L2 套餐（运营可配：三档打包 + 配额 + 席位）
L3 租户订阅（租户 → 套餐 + 有效期 + 状态）
L4 授权覆盖（按需：加购 / 试用 / 单点拒绝，带原因与失效时间）
```

判定顺序固定为 `熔断 → 租户拒绝 → 租户授权 → 套餐 → 默认关闭`，首个命中即返回，且必须返回**来源**（用于回答“为什么不让我用”）。

三条不可让步的约束：

1. **关闭是服务端拦截，不是隐藏按钮。** 403 + 明确错误码，前端隐藏只是体验优化。
2. **关闭不删数据，重开幂等。** 订阅降级是商务行为，不是数据清理。
3. **授权读取失败一律拒绝（fail-closed）。** 现有 4 处开关判断是 `ferr == nil && !ok`，即“读失败当作开启”，对合规开关属于漏放，必须一并修正。

## 2. 现状盘点（基于代码与库表核对）

| 现有资产 | 位置 | 能否直接支撑分级定价 |
|---|---|---|
| 灰度开关：`feature_flag(code, default_enabled, rollout_percent)` + `tenant_feature(tenant_id, code, enabled)` | `internal/feature/feature.go` | **不能**。语义是“发布控制”，混杂了百分比分桶；无法表达“买了/没买/试用到期/加购席位” |
| 开关种子：`share.external`、`share.email_verify`、`media.transcode`、`branding.custom_domain`，全部 `default=true, rollout=100` | DB | 只是“全部打开”，无商业语义 |
| 开关判断散落在 handler 内（4 处），失败策略不一致 | `handlers_share.go:113,163`、`handlers_media.go:63`、`handlers_platform_tenant.go:484` | **不能**。散点判断必然在新接口处漏判 |
| `tenant.plan text` | `tenant` 表 | **仅有字段**：创建/列表回显，无任何判定引用（`grep` 全仓仅 4 处，均为读写展示） |
| `tenant_quota(max_users, max_storage_bytes, max_transcode_seconds, max_api_calls_day, on_exceed)` | DB | 可复用为“档位内配额”，但要与能力授权解耦 |
| `metering`：`api_calls / transcode_seconds / share_views / preview_renders / egress_bytes` + `usage_daily` + 平台发票 CSV | `internal/metering` | 可复用计量管道，但**缺少三项能力各自的计费指标** |
| `classification`：`EffectiveClass`、`SetNode`、`RequestDown/Decide`、`SetPolicy` | `internal/classification` | 功能完整，但**嵌入 MAC 判定主链路**（`authz` 中 `sub.Class < obj.Class → CLASSIFICATION_DENIED`，先于 ACL） |
| `share`：`share_approval_min_class` 驱动审批；外链 + 邮箱验证 + 水印 + 外部分享转换 | `internal/share`、`handlers_share.go` | 密级与分享已耦合（审批阈值来自密级） |
| `directory`：每租户 AD 配置 + 同步 + 登录解析 | `internal/directory` | 已满足“多租户各自接域”，缺的是“能否使用”这一层许可 |

**结论**：底层零件齐备，缺的是**授权层**与**统一执行点**；`tenant.plan` 是空壳，`feature_flag` 不可复用为付费墙。

## 3. 模块边界定义

能力编码沿用现有风格（`域.能力`）。三项需求落到四个编码：

| 编码 | 名称 | 包含 | **不包含** | 依赖 |
|---|---|---|---|---|
| `share.external` | 对外分享（外链） | 创建/撤销外链、访问口令、次数与有效期、IP 白名单、审批、水印 | 通过邮件主动投递；访客邮箱验证码 | 核心 |
| `share.mail` | **邮件外发通道** | 收件人投递（Outbox）、外部分享的预览/编辑链接、邮件模板、投递失败重试与留痕 | 外链本身（无 `share.external` 则无链接可发） | `share.external` + 通知通道 |
| `auth.ad` | **AD 身份认证** | 目录配置、测试连接、全量/增量同步、域账号登录、组与部门映射 | 本地账号认证（永远可用，保证兜底入口） | 核心 IAM |
| `governance.classification` | **文件密级** | 密级标签体系、定密与降密审批、MAC 判定、按密级的分享审批阈值 | ACL（ACL 永远独立生效）；水印（属分享/预览） | 核心 authz + 分享（单向引用） |

另有两个既有开关的归位建议（不改变行为，只改归类）：

- `branding.custom_domain` → 商务能力（旗舰档卖点），当前 `default=true`，P1 起改为按套餐授予；
- `media.transcode` → 计量型增值（按秒计费），授权与配额分离：能开 ≠ 不限量；
- `share.email_verify` → 归入 `share.external` 的**安全增强子项**，不单独售卖，避免“买了外链却不能开验证”的组合尴尬。

### 3.1 边界划分的三条依据

1. **按“是否产生独立价值”切，不按代码目录切。** `share.mail` 与 `share.external` 在同一 handler 文件里，但一个是“能不能发链接”，一个是“能不能把链接送出去”，商业上可分开卖。
2. **依赖必须单向。** `share.mail → share.external`；`governance.classification → share.external`（仅审批阈值单向引用）。禁止反向依赖，否则无法单独关闭。
3. **核心能力不可授予。** IAM/ACL/内容/审计/预览基础能力无 `capability` 记录，天然不可关闭——它们一旦可关，系统就不成立。

## 4. 关闭语义与降级矩阵

关闭一个已售能力，必须回答四个问题：API 怎么回、存量数据怎么办、已发出的东西怎么办、重开是否幂等。逐模块定义如下。

| 模块 | 关闭后 API 行为 | 存量数据 | 已发出/已产生的外部产物 | 重新开启 |
|---|---|---|---|---|
| `share.mail` | 403 `FEATURE_NOT_ENABLED`；不再入队新邮件；外部分享页仍可访问 | 保留（`share`、`notification`） | **已发出的链接继续可用**，除非链接自身过期或被撤销 | 立即恢复，无迁移 |
| `auth.ad` | 域账号**拒登**（fail-closed，不回退本地口令）；同步任务停止调度；配置与同步记录只读 | 保留 `source='ldap'` 账号，不删、不改 | 现有会话按 TTL 自然到期，不强制踢出（避免营业时间集体掉线） | 立即恢复；建议立即跑一次全量同步 |
| `governance.classification` | 停止 MAC 判定（等价全员同级）；UI 隐藏密级列与按钮；密级相关审批接口 403 | 保留 `classification`、`classification_label`、`classification_change` | 分享审批阈值 `share_approval_min_class` **回退为“不需要审批”** | 原样恢复，无迁移 |

### 4.1 密级关闭的三档策略（**需业务拍板**）

密级不是普通增值功能，它是访问控制的一部分。关闭等价于“对高密文件解除一道防线”，因此提供三档：

| 档 | 规则 | 适用 | 代价 |
|---|---|---|---|
| **A 禁止关闭** | 租户存在 `classification > 0` 的对象时，禁止关闭 | 合同标记为合规要求（金融、政企） | 商务上少一个可回收项 |
| **B 强确认关闭**（推荐默认） | 允许关闭，但需：受影响对象清单（数量 + 最高密级）→ 平台双人确认 → 二次输入租户 slug → 审计 | 一般商业租户 | 存在“客户为省钱主动降合规”的风险，需在合同中约定 |
| **C 软关闭** | 只隐藏 UI，MAC 继续生效 | 不推荐 | 客户付了降级后的钱却仍受限，属于“假降级”，会引发投诉 |

**推荐**：默认 B；租户表增加 `compliance_required boolean`，为真时自动落到 A。

### 4.2 三条不可逆点（必须写进合同与界面）

1. `share.mail` 关闭**不会**让已发出的链接失效——避免“平台改配置，客户的外部合作方突然打不开”的商务事故。
2. `auth.ad` 关闭**不会**回退到本地口令——否则等于给出降级攻击面（改 DNS 或停目录即可绕过）。
3. `governance.classification` 关闭**不删除**任何密级标记——重新开启后立即恢复原状。

## 5. 数据模型

```sql
-- 能力目录：由迁移写入，运营不可新增（防止出现"没有实现的能力"）
capability(
  code            text primary key,          -- share.mail / auth.ad / governance.classification
  name            text not null,
  category        text not null,             -- share | identity | governance | platform
  description     text not null,
  depends_on      text[] not null default '{}',
  closable        text not null,             -- always | conditional | never
  meter_metric    text,                      -- 计费指标名，可空
  seat_based      boolean not null default false,
  sort_order      int not null default 100
)

-- 套餐：运营可配
plan(
  code        text primary key,              -- basic | standard | flagship | custom
  name        text not null,
  rank        int  not null,                 -- 用于"建议升级到哪一档"
  price_month numeric(12,2) not null default 0,
  currency    char(3) not null default 'CNY',
  seat_limit  int,                           -- null = 不限
  quota       jsonb not null default '{}',   -- 复用 tenant_quota 的字段形状
  visible     boolean not null default true
)

plan_capability(
  plan_code       text references plan(code) on delete cascade,
  capability_code text references capability(code),
  included        boolean not null default true,
  limits          jsonb not null default '{}',
  primary key (plan_code, capability_code)
)

-- 订阅：一个租户同时只有一个生效订阅
tenant_subscription(
  tenant_id          uuid primary key references tenant(id),
  plan_code          text not null references plan(code),
  status             text not null,          -- active | trial | grace | terminated
  started_at         timestamptz not null default now(),
  current_period_end timestamptz,
  trial_ends_at      timestamptz,
  seats              int,
  version            bigint not null default 1   -- 变更版本号，供缓存失效
)

-- 授权覆盖：只追加，不修改（可追溯）；求值取"最新一条未过期"
tenant_entitlement(
  id              uuid primary key default gen_random_uuid(),
  tenant_id       uuid not null references tenant(id),
  capability_code text not null references capability(code),
  effect          text not null,             -- grant | deny
  reason          text not null,             -- 必填：谁为什么给的
  granted_by      text not null,             -- 平台操作者
  seats           int,
  expires_at      timestamptz,
  created_at      timestamptz not null default now()
)
create index ix_ent_tenant_cap on tenant_entitlement(tenant_id, capability_code, created_at desc);
```

设计要点：

- **`tenant.plan` 不废弃，而是迁移到 `tenant_subscription.plan_code`**，旧字段保留一个版本用于回滚，读取以订阅表为准。
- **`tenant_entitlement` 只追加**：撤销 = 追加一条 `effect='deny'` 或写入 `expires_at`。这样“谁在什么时候因为什么放开的”永远可查。
- **不复用 `tenant_feature`**：那张表是布尔覆盖，无法承载有效期、席位、原因；强行扩展会让灰度与授权互相污染。

## 6. 授权求值服务

新增 `internal/entitlement`，唯一对外接口：

```go
type Source string // kill_switch | tenant_deny | tenant_grant | plan | default

type Decision struct {
    Allowed      bool
    Source       Source
    Reason       string     // 供界面与工单解释
    ExpiresAt    *time.Time // 试用/加购到期时间
    RequiredPlan string     // 命中默认关闭时，建议升级到哪一档
    Seats        int        // 席位型能力有效席位数
}

func (s *Service) Resolve(ctx context.Context, tenantID, code string) (Decision, error)
func (s *Service) ResolveAll(ctx context.Context, tenantID string) (map[string]Decision, error)
```

### 6.1 求值细节

1. **依赖校验内置于求值**：`Resolve(share.mail)` 时若 `share.external` 不为真，直接返回 `Allowed=false, Reason="依赖未启用"`。配置阶段也要拦（写入时校验依赖闭包），两道都做——配置可能被直接改库绕过。
2. **过期判断在求值时做**，不依赖定时任务。到期回收任务只是“清理展示状态”，不能是唯一防线（任务挂了就永久有效）。
3. **失败语义**：数据库读失败 → 返回错误，调用方回 **503 `ENTITLEMENT_UNAVAILABLE`**，不是 403。403 会让客户以为“没买”，实际是系统故障，一线无从分辨。
4. **缓存**：进程内 `map[tenantID]cachedSet{version, decisions}`。订阅或授权变更时 `version+1`（写在同一事务），求值先比版本、再比 30 秒 TTL。
   - 为什么不用 `LISTEN/NOTIFY`：多一条常驻连接与重连逻辑，换来的只是把 5 秒压到 1 秒；对“加购生效”这种场景，5 秒已经足够。
   - 为什么不纯 TTL：客户刚付款就被提示“未开通”，体验不可接受；版本号让本实例立即生效。

## 7. 执行点：一处判定，三处调用

| 层 | 位置 | 作用 |
|---|---|---|
| HTTP 路由声明 | `a.requireCapability(capShareMail, handler)` 包装 `ServeMux` 注册 | 唯一入口，新增接口必须显式声明能力，漏写即编译期不可见 |
| 服务层兜底 | 后台任务（dirsync 调度、Outbox 投递 worker、预览转换队列、ONLYOFFICE 回调） | 这些入口不经过 HTTP 中间件，必须各自调 `Resolve` |
| 前端展示 | `GET /v1/me/capabilities` | 仅决定“显示什么”，不作为安全边界 |

**错误契约**（前端与销售工具都依赖它）：

```json
// 403
{ "code": "FEATURE_NOT_ENABLED",
  "message": "当前套餐不包含「邮件外发」",
  "data": { "capability": "share.mail", "requiredPlan": "flagship",
            "upgradeHint": "升级到旗舰版即可开通", "contact": "sales@…" } }
```

```json
// 503
{ "code": "ENTITLEMENT_UNAVAILABLE", "message": "授权服务暂时不可用，请稍后重试" }
```

## 9. 定价分级与计量口径

| 档位 | 包含能力 | 配额（示例） | 定位 |
|---|---|---|---|
| 基础 `basic` | 核心 + `share.external`（含水印、审批、口令） | 50 用户 / 50 GB / 5 万 API 次/日 | 单组织内部流转 |
| 标准 `standard` | 基础 + `governance.classification` | 200 用户 / 200 GB | 有密级管理诉求 |
| 旗舰 `flagship` | 标准 + `auth.ad` + `share.mail` + `branding.custom_domain` | 500 用户 / 1 TB / 席位可加购 | 多部门、对接 AD |
| 定制 `custom` | 逐项 `plan_capability` 组合 | 按合同 | 大客户 |

**计量与授权的分离**（关键）：

- 授权回答“能不能用”，配额回答“能用多少”，两者独立配置、独立报错（403 vs 429）。
- 三项能力需要新增计量指标（现有 `metering` 的 CHECK 约束需同步扩展）：

| 能力 | 指标 | 用途 |
|---|---|---|
| `share.mail` | `email_sent` | 按封计费 / 反滥用限流 |
| `auth.ad` | `ad_active_users` | 席位计费（月活域账号） |
| `governance.classification` | `classified_objects` | 价值锚点（不直接计费，用于报价与续费说服） |

- 加购（add-on）走 `tenant_entitlement.seats/expires_at`，与 `tenant_quota` 解耦：加购 100 席位不等于放开存储上限。
- 试用（trial）走 `grant + expires_at`，到期自动失效；同时保留 `tenant.trial_ends_at` 作为商务展示字段，两者不一致时以 `entitlement` 为准（唯一事实源）。

## 10. 不变量（实现与测试都以此为准）

1. 依赖不满足 ⇒ 子能力不可为真（配置写入校验 + 求值二次校验）。
2. 关闭不删数据；重新开启后行为与关闭前一致（幂等）。
3. 商务能力不参与百分比灰度：`capability` 一旦进入售卖目录，`rollout` 恒为 100。灰度只作用于 `feature_flag` 的发布类开关。
4. 授权变更 ≤5 秒生效；求值失败 = 拒绝 + 503，不允许“读失败即放行”。
5. 任何授权变更（grant/revoke/plan change）必须落审计，含操作人、原因、有效期、变更前后值。
6. 已发出的外部分享不因 `share.mail` 关闭而失效。

## 11. 关键设计取舍

| # | 取舍 | 选择 | 理由 | 代价 |
|---|---|---|---|---|
| 1 | 复用 `feature_flag` 做付费墙 | **不复用**，新建 entitlement | 灰度是研发可改的发布控制，授权是合同约定；混用会导致“灰度没覆盖”被误解为“没购买”，客户投诉无法解释 | 两套机制并存，管理界面必须明确分区（“发布开关” vs “商业授权”） |
| 2 | 能力编码放代码还是让运营新增 | **代码 + 迁移** | 运营能新增就会出现“目录里有、代码里没有”的空能力，报价单会卖不出去的东西 | 新增能力需发版 |
| 3 | 关闭 = 硬拦截还是只隐藏 UI | **硬拦截** | 付费墙只靠 UI 等于没有控制；合规开关更必须服务端拦 | 销售演示需走临时授权流程（可给 7 天试用 entitlement） |
| 4 | 密级是否允许关闭 | **条件允许（B，合同标记则 A）** | 密级是访问控制，不是普通增值；无条件可关会制造“客户为省钱主动降合规” | 商务上少一个可回收项，需合同约定 |
| 5 | 席位粒度范围 | **仅 `auth.ad` 做席位** | AD 按人计费是真实诉求；三个模块都做席位会让授权模型复杂度翻倍 | 粒度不一致，界面需分别说明 |
| 6 | 过渡期如何避免影响现网 | **空授权表 = 现有行为** | 迁移期 `tenant_subscription` 为空时按“全部能力已授予”兼容，避免上线当天全体客户功能消失 | 需要一段有期限的兼容开关，且必须有下线日期 |

## 12. 落地阶段与回滚

| 阶段 | 内容 | 验收标准 | 回滚 |
|---|---|---|---|
| **P0 目录化** | `capability` 表 + 迁移种子；现有 4 个开关分类标注；抽出统一 `requireCapability` 执行点（先恒返回真） | 行为零变化；现有 AC 全绿 | 删除包装器即可 |
| **P1 授权服务** | `internal/entitlement` + 订阅/授权表 + 三模块接入 + fail-closed 修正 + 503 语义 | 关闭模块后 API 403、数据保留、重开恢复；读失败返回 503 | 清空 entitlement 表 + 关闭兼容开关 |
| **P2 套餐与平台 UI** | `plan/plan_capability` + 平台四组接口 + 审计 + 租户“能力与升级”页 | 改套餐 5 秒内生效；审计可查变更前后值 | 订阅表回滚到默认档 |
| **P3 计费联动** | 三个新 metric + 席位统计 + 试用自动回收 + 发票行项目 | 月度发票能按能力拆分；试用到期当天失效 | 停止写入新 metric（不影响旧数据） |

**兼容开关**：`DOCVAULT_ENTITLEMENT_LEGACY_ALL=1`（默认开，建议 2 个版本后删除）。为真且租户无订阅记录时，视为“全部能力已授予”。这是为了让升级当天不发生客户功能消失，但必须设下线日期，否则这套机制永远不生效。

## 13. 风险与开放问题

### 13.1 已识别风险

1. **组合爆炸**：3 模块 × 开关状态 × 历史数据状态，测试矩阵会迅速膨胀。缓解：只允许“模块级开关”，不做能力内部的细粒度开关；用 §10 六条不变量收敛用例。
2. **计费与授权不一致**：客户付钱但被拦、未付钱却能用。缓解：`entitlements/effective` 对账接口 + 每日巡检任务比对“套餐应有 vs 实际求值”。
3. **降级期间的数据暴露**：密级关闭会放开一道防线。缓解：B 档强确认 + 影响清单 + 审计；合同标记走 A 档。
4. **缓存不一致**：多实例部署时版本号只能保证本实例立即生效。缓解：TTL 30 秒兜底，并在授予接口返回“预计 5 秒内生效”。

### 13.2 需要你拍板（这四条决定实现细节）

1. **密级关闭策略**：A（有定密数据即禁止）/ B（强确认关闭，推荐）/ C（软关闭）。是否引入 `compliance_required` 租户标记？
2. **`auth.ad` 关闭时，已同步的域账号如何处理**：拒登（推荐，安全）/ 一次性降级为本地账号（需生成随机口令 + 强制改密）/ 保持登录直到会话过期？
3. **席位是否只做 AD**：若未来「邮件外发」也要按人计费，现在就要把 `seat` 设计成通用字段（已预留），但统计口径不同，需确认。
4. **三档的具体边界与报价锚点**：本文档给的是示例划分，实际以商务为准；我需要在 P2 之前拿到最终打包清单，否则 `plan_capability` 只能填占位。

## 14. 与其他设计文档的关系

- 本文只解决“**能力是否可用**”，不改变 `docs/15`（目录认证）与 `docs/16`（登录方式）的功能语义；`auth.ad` 关闭时的行为以本文 §4 为准。
- 密级的判定逻辑仍在 `internal/authz`，本文只增加“是否执行 MAC”这一层闸门；关闭时 `authz` 跳过 MAC 步骤并在判定链路里显式标注 `classification=skipped`，便于审计回溯。
- 计费口径扩展需与 `docs/09-平台运营手册` 的用量对账章节同步修订（P3）。
