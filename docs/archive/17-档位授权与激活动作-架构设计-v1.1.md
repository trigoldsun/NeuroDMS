## 1. 档位模型

三档由低到高，**档位是代码内置枚举，不是运营可新增的记录**：

| 档位 `edition` | 名称 | 密级等级集 | AD 认证 | 邮件外发 | 自定义域名 | 媒体转码 |
|---|---|---|---|---|---|---|
| `basic` | 基础版 | **无**（对象密级恒 0） | 无 | 无 | 无 | 按配额 |
| `professional` | 专业版 | **3 档：公开 / 秘密 / 机密** | 有 | 无（待确认） | 无 | 按配额 |
| `business` | 商业版 | **7 档：公开…核心**（现有全集） | 有 | 有（待确认） | 有 | 按配额 |

设计要点：

1. **档位 → 能力集是一张编译进程序的矩阵**（`editionMatrix`），只允许评审时改。运营可以改价格、改配额、改有效期，但不能改“这一档含哪些能力”——否则同一个档位在不同客户处含义不同，客服与报价单必然打架。
2. **配额与能力解耦**：能力回答“能不能用”（403），配额回答“能用多少”（429）。档位同时给出二者的默认值。
3. **档位不叠加**：不存在“专业版 + 单独买 AD”。若商务确需，用“例外授权”（§3.6），仍记录为对该档位的例外，而不是新造一个第四档。

## 2. 密级按档位：同一把尺子，档位只裁剪可选集

这是本稿最需要评审确认的一点，因为做错会造成**升级即降密**的安全事故。

### 2.1 现有刻度（不可改）

`node.classification` / `space.classification` 是 `smallint CHECK 0..6`，等级语义固定，只允许改显示名：

| level | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| 名称 | 公开 | 内部 | 敏感 | 秘密 | 机密 | 绝密 | 核心 |

`authz` 的 MAC 判定是**数值比较**（`user.Class < obj.Class` 即拒绝）。现有库中已有 level 2、3 的对象。

### 2.2 三档的映射（推荐：按同名对齐）

| 档位 | 可选密级集 | 说明 |
|---|---|---|
| 基础版 | 不可用 | 隐藏密级 UI；对象恒 0；MAC 恒通过 |
| 专业版 | `{0 公开, 3 秘密, 4 机密}` | 三个选项，语义与七档**同名同义** |
| 商业版 | `{0..6}` 全集 | 现有行为不变 |

### 2.3 为什么不做“三档压缩存储”

一种看似简单的做法是：专业版把密级存成 `0/1/2`（公开/秘密/机密），升级到商业版时迁移成 `0/3/4`。**不能这样做**：

- 迁移是一次性不可逆的数据改写，期间并发写入必然错位；
- 升级当天只要有一条迁移失败，文件就会落到错误的等级；
- 更糟的是“看起来对”：如果升级时漏迁，level 2 在七档里是「敏感」，而专业版的 2 是「机密」——**降密却无人察觉**。

采用“同一把尺子”后：

- **升级（专业版 → 商业版）**：可选集从 3 个扩到 7 个，存量数值不动，零迁移；
- **降级（商业版 → 专业版）**：若存在 `1/2/5/6` 的对象，**拒绝降级**并列出清单；客户可先走现有“降密审批”把对象降到 3/4，再降档；
- **降级（→ 基础版）**：只要存在 `>0` 的对象即拒绝。

代价：专业版可选的三个刻度是 0/3/4，中间跳过了 1/2，看起来“不连续”。这是有意的——它保证了跨档升级不发生语义漂移。若业务坚持“专业版的机密必须是最高级”，则应改为 `{0,3,6}`，但必须接受“升级后原‘机密’显示为‘核心’”的名称变化，需在合同中写明。

**结论**：MAC 判定代码完全不用改，档位差异只体现在“写入口允许哪些值”。这是本方案最省事也最安全的地方。

## 3. 激活动作设计

### 3.1 两种部署形态，同一套抽象

| 形态 | 激活方式 | 签发方 | 校验方 |
|---|---|---|---|
| 本地部署（单实例） | 管理员导入**许可证文件**（离线） | 厂商 | 服务自身（内嵌公钥） |
| SaaS（多租户） | 平台控制台把租户改为某档 | 平台运营 | 服务自身（同一条 license 记录） |

SaaS 也生成一条 license 记录（不落文件），这样两条路径共用同一个校验器，避免“线上能用、线下不能用”的双实现漂移。

### 3.2 许可证结构

```json
{
  "v": 1,
  "licenseId": "LIC-2026-000123",
  "customer": "某某科技有限公司",
  "deployment": "onprem",              // onprem | saas
  "instanceId": "0f3c…",               // onprem 必填；saas 为 null
  "edition": "professional",
  "seats": 200,                        // 可选，见 §7 说明
  "limits": { "maxUsers": 200, "maxStorageGB": 200, "maxApiCallsDay": 50000 },
  "notBefore": "2026-11-01T00:00:00Z",
  "expiresAt": "2027-10-31T23:59:59Z",
  "issuedAt":  "2026-10-28T09:00:00Z",
  "sig": "base64(Ed25519(canonical(payload)))"
}
```

### 3.3 五个必须做对的细节

1. **用 Ed25519 签名，不用 HMAC。** HMAC 的密钥必须在校验侧，而校验侧就在客户机器上——等于把伪造能力交给客户。Ed25519 只把公钥编译进程序，私钥留在签发侧。
2. **签名对象是 canonical JSON**（键排序、无多余空白、UTF-8 NFC）。否则改一个空格就失效，或换一种序列化方式就能绕过校验。
3. **绑定实例指纹，不绑定 MAC/CPU 序列号。** 指纹 = 首次启动生成的随机盐 + 主机名 + 操作系统标识，存库；换机或重装需重新签发（常见商务要求）。绑硬件会在虚拟化/网卡变更时误失效，运维成本远高于收益。
4. **防时间回拨。** 记录 `last_seen_at` 单调递增；系统时间比上次记录倒退超过 24 小时 → 进入宽限（仍可用）并告警，不直接停服。用定时任务+DB 时间戳，不信任本机时钟。
5. **幂等激活。** 同一 `licenseId` 重复导入 → 覆盖同一条记录，不产生新历史；不同 `licenseId` → 追加并生效。激活历史只追加，永不删除（审计要求）。

### 3.4 未激活 / 到期 / 降档的状态机

```
未激活 ──导入有效许可证──> 已激活 ──到期──> 宽限 30 天 ──> 降为基础版
   │                          │
   └──（default）─────────────┴──导入更高档──> 已激活（档位提升）
                              └──导入更低档──> 兼容性校验 ──不通过──> 拒绝（保持原档）
                                              └──通过──> 已激活（档位下调）
```

关键取舍：

- **未激活 = 基础版可用**，不是“装完打不开”。否则一次导入失败就等于系统不可用，支持成本极高。
- **到期 = 降为基础版 + 保留全部数据**，不是停服。停服会让客户的数据无法导出，属于商业与法律风险。
- **降档必须先通过兼容性校验**（§2.3），不通过则拒绝激活并返回影响清单，而不是“先降再报错”。

### 3.5 接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/v1/admin/license` | sysadmin | 当前档位、有效期、能力集、实例指纹、到期剩余天数 |
| POST | `/v1/admin/license/activate` | sysadmin | 导入许可证（onprem）；body = 许可证原文 |
| GET | `/v1/platform/tenants/{slug}/license` | 平台读 | 查看租户档位与历史 |
| PATCH | `/v1/platform/tenants/{slug}/edition` | 平台写 | 改档（saas 路径），触发同一套校验 |

### 3.6 例外授权（退居次要）

仅用于：试用（30 天）、故障补偿、单点试用某能力。形成 `tenant_entitlement` 记录（只追加，带原因与 `expires_at`），求值时优先级高于档位，低于全局熔断。**不允许**用它长期拼出一个“第四档”。

### 3.7 审计

`license.activate` / `license.rejected`（含拒绝原因）/ `edition.change`（含前后值）/ `entitlement.grant`。写入现有哈希链审计表。

## 4. 执行点（沿用 v1.0，仅调整数据源）

| 层 | 位置 | 说明 |
|---|---|---|
| HTTP 路由 | `a.requireCapability(cap, handler)` | 唯一入口；能力由 `edition` 解析而来 |
| 服务层 | dirsync 调度、Outbox worker、预览转换队列、ONLYOFFICE 回调 | 非 HTTP 入口必须各自校验，否则绕过 |
| 写入口参数校验 | 密级写入、成员创建、目录配置保存 | 档位限制“能写成什么值”（如专业版只允许 0/3/4） |
| 前端 | `GET /v1/me/capabilities` | 只决定显示，不是安全边界 |

错误契约沿用：`403 FEATURE_NOT_ENABLED`（附 `edition` 与建议升级档位）/ `503 ENTITLEMENT_UNAVAILABLE`（授权读取失败，fail-closed）。

## 5. 数据模型

```sql
-- 激活记录：每个实例/租户一条当前生效记录 + 无限追加的历史
license_activation(
  id            uuid primary key default gen_random_uuid(),
  tenant_id     uuid references tenant(id),        -- saas 必填；onprem 可空（单实例）
  deployment    text not null,                     -- onprem | saas
  instance_id   text,                              -- onprem 指纹
  license_id    text not null,
  edition       text not null check (edition in ('basic','professional','business')),
  seats         int,
  limits        jsonb not null default '{}',
  not_before    timestamptz,
  expires_at    timestamptz,
  raw           jsonb not null,                    -- 原始 payload（不含 sig 亦可）
  signature     text not null,
  status        text not null,                     -- active | superseded | expired | rejected
  activated_by  text not null,
  activated_at  timestamptz not null default now()
);
create index ix_license_tenant on license_activation(tenant_id, activated_at desc);

-- 实例指纹（onprem）
instance_identity(
  instance_id text primary key,
  salt        text not null,
  created_at  timestamptz not null default now(),
  last_seen_at timestamptz not null default now()   -- 防时间回拨
);
```

`tenant.plan` 保留为展示字段（与最新激活记录同步），不参与判定。

## 7. 关于“席位”（回答上一轮问题 3）

**席位（seat）= 允许使用系统的用户数上限**，按人头计费，与“功能”是两个维度。

我上一轮问它的原因：AD 接入在业内常按“域账号数”单独卖（因为域账号往往包含大量只读/临时账号），而密级、邮件外发通常按实例或按功能卖。若两者混在一起，会出现“客户有 500 个域账号但只买 100 席”这种无法表达的情况。

**建议（最简）**：不引入独立席位概念，三档各自给一个 `maxUsers` 上限（复用现有 `tenant_quota.max_users`）。理由：系统已经有 `active_users` 计量与配额拦截，够用；多一层席位会带来“席位超限时是拒绝新建用户还是拒绝登录”的额外决策。

**若商务确实要按 AD 账号数单独报价**，则只在 `auth.ad` 上加一个子配额 `ad_seats`，其余模块不引入席位——避免每个能力都要一张席位表。

需要你回答：**是否有“按人数分档报价”的需求？**（有 → 我加 `ad_seats`；无 → 只用 `max_users`。）

## 8. 关于“打包清单”与“报价锚点”（回答上一轮问题 4）

两个词的含义：

- **打包清单**：一张“三档 × 功能点”的表，明确每一档**具体含哪些功能**。它就是 §6 `editionMatrix` 的内容，一旦确定，代码里就写死。
- **报价锚点**：每一档的**计价单位与价格区间**（例如：基础版 2 万/年/实例，专业版 5 万/年 + 50 元/用户/年，商业版 12 万/年）。它决定“这个功能放在哪一档才卖得动”，也决定界面上的升级引导文案。

我问它的原因：`editionMatrix` 的默认值必须有依据；如果由我按技术合理性填，可能与商务定价冲突，届时改一次要发一次版。

**建议先按下表定稿（可直接修改后回复我）**：

| 功能 | 基础版 | 专业版 | 商业版 |
|---|---|---|---|
| 内容与版本、权限（ACL）、审计链、预览/水印 | ✅ | ✅ | ✅ |
| 对外分享外链（口令、次数、有效期） | ✅ | ✅ | ✅ |
| 分享邮箱验证码 | ✅ | ✅ | ✅ |
| **文件密级** | ❌ | ✅ 三档 | ✅ 七档 |
| **AD/LDAP 认证** | ❌ | ✅ | ✅ |
| **邮件外发通道**（把链接发给外部人） | ❌ | ❌ | ✅（待你确认） |
| 自定义域名 / 白标 | ❌ | ❌ | ✅ |
| 音视频转码 | 按配额 | 按配额 | 按配额 |
| 用户数上限（`max_users`） | 50 | 200 | 500 |

唯一需要你拍的是“**邮件外发放在专业版还是商业版**”——它直接决定专业版能否对外发链接，是三个功能里最影响成交的一项。

## 9. 不变量

1. 档位只决定能力集与参数，不改变既有数据语义；跨档升级零迁移。
2. 降档必须先通过数据兼容性校验，不通过则拒绝激活。
3. 未激活/到期 = 基础版可用 + 数据保留，不停服、不删数据。
4. 授权读取失败 = 拒绝 + 503，不允许 fail-open。
5. 激活、改档、例外授权全部落审计（含前后值与操作人）。
6. 已发出的外部分享不因档位变化而失效。

## 10. 关键取舍

| # | 取舍 | 选择 | 理由 | 代价 |
|---|---|---|---|---|
| 1 | 能力逐项授予 vs 档位整体授予 | **档位整体** | 三档是商务契约，逐项配置会让“同名档位内容不同”，报价与客服无法对齐 | 单点加购必须走例外授权，流程略重 |
| 2 | 专业版密级：压缩存储 vs 同一把尺子 | **同一把尺子（0/3/4）** | 跨档升级零迁移，杜绝“升级即降密” | 专业版可选值不连续，需向客户解释 |
| 3 | 许可证：签名 vs 加密 | **签名 + 明文字段** | 离线可验、客服可直接读字段排障 | 客户能看到档位与席位（无敏感性） |
| 4 | 绑定：实例指纹 vs 硬件 | **实例指纹** | 硬件变更不误失效 | 换机需重新签发 |
| 5 | 到期：停服 vs 降为基础版 | **降档 + 保留数据** | 停服会造成数据取不出，法律风险高 | 需要处理“降档后密级对象”的兼容性 |
| 6 | 席位：独立概念 vs 复用 max_users | **复用（默认）** | 少一层概念，现有配额拦截可直接用 | 无法表达“AD 单独按人卖”（如需要再加子配额） |

## 11. 落地阶段

| 阶段 | 内容 | 验收 | 回滚 |
|---|---|---|---|
| **P0** | `license_activation` 表 + `edition` 解析 + `requireCapability` 执行点（恒返回 business） | 行为零变化 | 删除包装器 |
| **P1** | 许可证校验（Ed25519）+ 激活接口 + 档位矩阵 + 密级写入口按档位限制可选值 | 三档各自验证：基础无密级、专业 0/3/4、商业 0..6 | 清空激活表 → 回落 business |

| **P3** | 到期降档任务 + 宽限期 + 例外授权（试用） | 到期当天降为基础版且数据完好 | 手工续期 |
