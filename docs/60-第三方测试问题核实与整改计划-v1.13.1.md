**最重要的三点判断**：

1. **F-09 的真实根因比报告更具体**：`web/src/pages/ShareView.tsx:138` 先按 `resp.status === 428` 判定为口令门，而 `VERIFY_REQUIRED` 同样是 428，导致第 141 行的 `setPhase('verify')` **永远不可达**。这是"状态码二义 + 判定顺序错误"，不是"未实现邮箱验证流程"——流程与 UI 都在（第 471 行有 verify 渲染块），只是进不去。
2. **F-03 是确认的数据完整性缺陷，且修复成本极低**：`EditMember` 组件用 `useState(member.字段)` 初始化且**没有 `key={member.id}`、没有跟随 prop 的 `useEffect` 重置**。在不关闭抽屉的情况下切换编辑对象，组件不卸载，提交时会把**上一次挂载时**的成员数据写进新目标 —— 与报告"两次 PATCH 载荷均为第三人数据"的现象完全吻合。增加 `key={member.id}` 即可消除。
3. **F-13 的核心事实被误判，但结论方向正确**：降密申请端点**存在**（`POST /v1/nodes/{id}/classification/requests`，另有两个管理端端点），报告测试的是 `/v1/classification/requests` 这类**不存在的全局路径**，因此判定"端点 404"。真正的问题是两个：**前端没有提交表单**、**错误文案泄露内部路由**（`handlers_classification.go:199` 把路径写死进 message）。

### 2.2 P2

#### F-03 编辑成员串扰（数据污染）

**判定：确认，建议按 P1 处理｜报告"加重"判断成立**

`web/src/pages/Members.tsx` 的 `EditMember`：

```tsx
function EditMember({ member, ... }) {
  const [f, setF] = useState({
    displayName: member.displayName, email: member.email, ...
  })   // ← 仅首次挂载时生效
```

调用处（同文件 350 行）：

```tsx
{editing && <EditMember member={editing} ... />}
```

- 无 `key={member.id}` → 切换 `editing` 时 React 复用同一实例，`useState` 初值不再执行；
- 无 `useEffect(() => setF(...), [member.id])` → 表单停留在**首次挂载的那个成员**的数据；
- 提交走 `PATCH /v1/admin/members/{新目标 id}`，载荷却是旧成员的数据 → 服务端 200 接受 → **静默写坏新目标**。

这与报告"连续编辑 lisi→wangwu，两次载荷均为 locktest 的数据"完全一致（locktest 是那轮最先打开的对象）。

**补充实测（1.12.1 验证轮）**：编辑抽屉是全屏遮罩（`modal-mask`，点击即关闭）。用浏览器实测——抽屉打开时**自然点击下一行「编辑」会被遮罩拦截**（Playwright 等待 8 秒超时，未发生点击）。因此：

- 该串扰在**真人操作路径下不可达**（必须先关闭抽屉，组件卸载重建，不会串扰）；
- 报告的复现很可能借助了**程序化穿透点击**（自动化工具的 force click / dispatchEvent），这属于测试方法产生的触发条件；
- 结论：**根因成立、修复有效，但实际风险低于报告描述**。定级建议 **P2**（数据完整性后果严重，但触发条件苛刻，且 1.12.1 已修）；报告建议"按 P1 对待"可保留为关注项，不必阻断发布。

#### F-06 /files 徽标闪现"未登录 密级 0"

**判定：确认｜`web/src/components/Shell.tsx:251-252`**

```tsx
<b>{me?.displayName || me?.username || '未登录'}</b>
<small>密级 {me?.classification ?? 0} · 账户设置</small>
```

#### F-07 不可预览格式（ZIP）提示

**判定：部分成立｜文案已改，能力判定缺失**

- `web/src/pages/PreviewPage.tsx:122` 已有"该类型暂不支持在线预览，请下载后本地查看"分支；

#### F-08 文本分享声明水印但无实现

**判定：确认｜`web/src/pages/ShareView.tsx`**

`watermark` 仅用于两处文案：`327` 行（"已开启水印"）与 `388` 行（"页面已叠加溯源水印"）。全文**没有任何水印渲染层**（无 canvas / overlay / 伪元素 / 背景）。PDF 走的是预览服务端叠加，文本走前端直出，因此文本分享的声明不成立。**属实**。

#### F-09 邮箱验证分享被渲染为口令门

**判定：确认，且已定位到报告未指出的精确根因｜P1 级别应提升**

```tsx
136:  if (resp.status === 410) return setPhase('gone')
138:  if (code === 'PASSWORD_REQUIRED' || resp.status === 428 || resp.status === 411) return setPhase('password')
141:  if (code === 'VERIFY_REQUIRED') return setPhase('verify')          // ← 永远不可达
```

服务端对"需邮箱验证"返回 **428 + `VERIFY_REQUIRED`**（与"要口令"共用 428，见接口约定）。第 138 行按状态码无条件拦截，第 141 行的 code 判断成为死代码；第 196 行（票据兑换路径）同样写法。UI 侧的验证流程（471 行 `phase === 'verify'`）**已实现**，只是进不去。

**结论**：这不是"流程未实现"，而是**判定顺序错误 + 428 语义二义未按 code 区分**。修复为两行：先判 `code`，再判状态码。

#### F-11 成员页无停用/删除/重置口令；PATCH status 静默忽略

**判定：部分成立（界面已补齐；`PATCH` 静默忽略仍存在）**

| 子项 | 核实 |
|---|---|
| 界面入口 | ✅ 已有「更多操作」菜单（复测确认），并有专用端点 `POST /v1/admin/members/{id}/status` |
| PATCH 静默忽略 | ✅ **仍存在**：`internal/httpapi/api.go:576` 的 `decode` 使用普通 `json.Decoder`，**未启用 `DisallowUnknownFields`**，`{"status":"disabled"}` 这类字段被静默丢弃并返回 200 |

> 这是**系统性问题**，不止成员接口：所有写接口都会静默忽略拼错的/不支持的字段。整改应统一在 `decode` 层加"拒绝未知字段"，而不是逐个 handler 补校验（代价大且会漏）。

#### F-12 审批人资格与手册不一致

**判定：确认｜根因是档位位集与手册口径不一致**

`internal/authz/bit.go:143`：

```
PresetManager: Display | Preview | Download | Print | Create | Copy | Edit | Rename | Move | Delete | ShareInternal | ManageVersion   // 12 位，不含 ManageACL
```

而审批人候选判定要求 `authz.ManageACL`（`share_approvers.go` 内 `Authorize(..., ManageACL, ...)`）。因此 **manager 档永远不进候选池**，与报告实测一致；手册 §7.2 写"管理者或所有者档位"，两者矛盾。

另：`shareApprover` 只有 `Eligible bool`（且仅对 `owners` 使用），**没有 `ineligibleReason` 字段**，报告此点成立。

**这是产品口径问题，需在两条路中选一条**（见整改计划 A-12）。

#### F-15 账号锁定后无提前解锁手段

**判定：确认｜`grep -rn "unlock" internal/` 无业务端点**（仅见 `sync.Mutex.Unlock`）。成员菜单无解锁项，`POST /v1/admin/members/{id}/unlock` 404。锁定机制本身正确（5 次 → 429）。**属实**。

#### F-16 MFA 限流以 500 呈现

**判定：确认（已定位根因并修复）｜报告归因正确，我此前的"无 MFA 限流器"判断有误**

- 复现结果（1.13.0 验证轮）：新建 MFA 账号连续登录 7 次，状态为 `202×5 → 500:INTERNAL ×2`，与报告完全一致。
- 根因：限流不在 HTTP 中间件层，而在 **OTP 签发层**——`internal/auth/otp.go` 按 `MaxPerWindow` 计数，超限返回 `ErrTooManyCodes`，而 `writeAuthErr` 的 switch **没有这个分支**，落到 `default` 被包装成 500「处理失败」。
- 我此前"无 MFA 限流器"的判断是错的：限流存在，只是不在我检索的关键词范围内（在 `otp.go` 而非 `handlers_auth`）。报告"限流以 500 呈现"的归因**正确**。
- 修复（1.13.0）：`writeAuthErr` 增加 `ErrTooManyCodes` → **429 `CODE_TOO_FREQUENT` + `Retry-After: 60`**。
- 复验：同一账号再次登录 → `429 CODE_TOO_FREQUENT`（带 retry-after=60）。

| **R-02** | 降密错误文案写死内部路由 | 用户看到无法执行的路径；且该路径本身错误 | `handlers_classification.go:199` |
| **R-03** | F-09 的 428 二义在**两处**存在（首屏与票据兑换） | 只修一处仍会复发 | `ShareView.tsx:138`、`196` |
| **R-04** | 审计历史缺口无法回填（哈希链） | 合规文档需显式声明缺口区间，不能承诺"全程可追溯" | `audit_event.prev_hash/hash` |

### 2.5 报告方法层面的问题（导致误报的原因）

1. **端点存在性靠猜路径**：F-13 的 404 结论来自尝试 `/v1/classification/requests` 等路径。正确做法是先取路由表（源码 `HandleFunc` 清单或 OpenAPI），再验证语义。本次核实用 `grep HandleFunc` 即得真实路径。
2. **未记录部署基线**：报告未记录被测镜像/提交号，导致"复测已修复/未修复"无法与具体版本对齐。本次核实固定为 `1.12.0 / a64c4ca`。
3. **状态码单独判定**：428 在这个系统里是二义的（口令 / 邮箱验证），只看状态码必然误判，报告对 F-09 的判断恰好绕过了这个坑（它按 code 描述），但把根因归为"未实现"而非"判定顺序"。
4. **环境变更与结论混排**：套餐升级、admin 密级调整属环境动作，报告已声明，但仍把 F-02 计入缺陷清单，容易在交付评审时被误读为产品缺陷。

## 五、结论

1. 报告的整体质量较高：**11 项确认成立**，其中 F-03（数据污染）、F-09（分享不可用）、F-13（降密不可用）三项判断准确且价值高；对"服务端正确、前端呈现错误"的分离做得尤其到位（F-09）。
2. **一处误报需纠正**：F-13 的"端点不存在"——真实端点是 `POST /v1/nodes/{id}/classification/requests`，报告测的是不存在的全局路径。整改因此从"新建后端"降级为"补前端表单 + 改文案"，工作量差一个量级。
3. **一处归因需修正**：F-16 的"限流返回 500"缺乏代码依据（系统无 MFA 限流器，IP 限流返回 429），500 更可能是 SMTP 失败被通用错误包装；需运行时复现后定性。
4. **一项非缺陷**：F-02 在当前代码中已按"开通即给档位最高密级"实现，该租户为历史数据。
5. 整改的核心不是补功能，而是**修三处"差一行"的缺陷**（编辑抽屉 key、428 判定顺序、decode 严格性）与**补两处"有承诺无入口"**（降密表单、账号解锁）。
