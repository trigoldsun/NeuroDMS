## 0. 一页结论

**现有系统"管得住、看得见"，但"签不了、证不清、留不久"。**

| 判断 | 依据 |
|---|---|
| **管得住** ✅ | 15 位原子权限、密级优先（MAC）、显式拒绝、就近继承、三权分立、租户 RLS 隔离、外发审批 |
| **看得见** ✅ | 审计事件序号链 + 哈希链 + Merkle 日结锚点、只追加规则、证据包导出、预览水印 |
| **签不了** ❌ | 全系统没有电子签名：没有签名人身份绑定、没有签名含义、没有签名与记录的密码学绑定 |
| **证不清** ❌ | 日结锚点用 **HMAC（对称密钥）**，密钥在系统内，第三方无法独立验证；没有 RFC 3161 可信时间戳，"某时刻已存在"无法自证 |
| **留不久** ❌ | 审计默认只留 **2 年**（GxP 常见 5 年以上）；版本可被保留策略清理；没有记录声明、法务冻结、销毁审批、归档信息包 |

**四个阻断级缺口**：① 无电子签名；② 无可信时间戳与非对称锚点；③ 无记录生命周期（声明/保留/冻结/处置）；④ 无系统验证证据包（CSV）。

**建议分四期**，不要一次宣称"符合 21 CFR Part 11"——Part 11 是"软件能力 + 组织 SOP + 验证证据"三者之和，软件只占其中一部分。

| 期次 | 主题 | 周期 | 一句话目标 |
|---|---|---|---|
| P0 | 可信底座 | 4–6 周 | 让审计链**可被第三方独立验证**，让记录**不可改、按期留** |
| P1 | 电子签名 | 6–8 周 | 让"谁在何时以什么含义签了哪份内容"**可签、可验、可举证** |
| P2 | 归档与长期保存 | 6–8 周 | 让记录**脱系统可读、可检测、可保存 10 年以上** |
| P3 | 验证与认证 | 8–12 周 | 让客户 QA **拿得走一套验证包**，直接引用 |

## 1. 调研范围与方法

### 1.1 假设

NeuroDMS 目前定位"文档合规管理"，客户群横跨制药/医疗器械、临床研究、工程质量、法务合同。不同行业对"电子签名强度"的要求差异极大：

- 内部审批、一般合同：**高级电子签名（AdES）** 足够；
- GMP 批记录、放行、临床知情同意、对外法定文件：通常要求 **可靠电子签名 / QES**；
- 普通内部流转记录：**平台内签名 + 强审计**即可，但要能证明"未被篡改"。

因此方案采用**分级签名**（L1/L2/L3），而不是一刀切上最贵的 QES。

### 1.2 方法

按"法规条款 → 控制目标 → 系统能力 → 可出示的证据"四层拆解。任何一条要求，如果不能落到"客户能拿给检查员看的东西"，就不算被满足。

### 1.3 术语约定

- **记录（record）**：需要留存、可作为证据的电子对象（本文中一份文件的一个版本即可构成一条记录）。
- **签名（signature）**：绑定到具体记录、表达特定含义（编制/审核/批准/放行/知悉）的行为及其凭证。
- **可信时间（trusted time）**：由第三方时间戳机构签发、不依赖本系统时钟的时间证明。

## 3. 核心合规要求：把法规翻译成控制目标

### 3.1 ALCOA+ 九项与系统落点

| 原则 | 含义 | 系统必须提供的能力 |
|---|---|---|
| Attributable 可归因 | 谁做的 | 唯一账号、不可共享、操作者身份写入每条记录与审计 |
| Legible 清晰 | 可读、可理解 | 可读的审计呈现、导出 PDF/JSON、非 DBA 也能看懂 |
| Contemporaneous 同步 | 当时记录 | 服务端时间 + 可信时间戳；禁止事后补录而不留痕 |
| Original 原始 | 原始记录或真实副本 | 原件不可覆盖；副本需经验证的"真实副本" |
| Accurate 准确 | 无错误 | 关键数据二次校验；内容哈希；版本对比 |
| Complete 完整 | 不缺失 | 元数据、附件、签名、审计一并保存 |
| Consistent 一致 | 自洽、可复现 | 序号连续、哈希链可复算、时间单调 |
| Enduring 持久 | 介质可读 | WORM、格式迁移、长期验证 |
| Available 可获得 | 需要时取得到 | 保留期内可检索、可导出、可验证 |

### 3.2 "可靠电子签名"的四要件（中国法）与三种法规的对应

| 中国《电子签名法》第 13 条 | eIDAS Art.26 | Part 11 §11.200 | 系统落点 |
|---|---|---|---|
| ① 签名制作数据属于签名人专有 | 唯一关联签名人 | 签名唯一于个人、不得转授 | 一人一证书/一密钥，绑定实名身份 |
| ② 签署时仅由签名人控制 | 签署人单独控制 | 两个识别组件；仅本人使用 | 签署时重认证（口令 + 第二因子）；私钥在签名人设备/云签 HSM |
| ③ 签署后对签名的任何改动可被发现 | 改动可检测 | 签名与记录绑定，不可剪除转移 | CMS/PAdES 密码学签名；签名覆盖签名值本身 |
| ④ 签署后对内容与形式的任何改动可被发现 | 同上 | 同上 | 签名覆盖内容哈希 + 元数据摘要；改一个字节即验证失败 |

> 这四要件不是"四个功能"，而是**一个密码学闭环**：身份 → 密钥 → 签名 → 绑定 → 可验证。缺任何一环，前四者都不成立。

### 3.3 审计追踪的六个必备属性

1. **系统生成**：不是应用"记得写"，而是数据库层面拒绝绕过（当前已用规则 + 权限实现）。
2. **带时间戳**：服务端时间只能作为"系统时间"，对外举证需第三方可信时间。
3. **独立于操作者**：操作者不能关闭、编辑、删除审计（当前已实现"只追加"）。
4. **不掩盖原值**：变更需保留 old/new 与**原因**（当前缺"原因"字段）。
5. **可读**：检查员/审计员不需 DBA 即可查询与导出（当前有列表与证据包，但缺"定期审阅"工作流）。
6. **与记录同寿命**：审计留存 ≥ 被审计记录的留存期（当前默认 2 年，是缺口）。

### 3.4 记录生命周期（最容易被忽略的一段）

```
创建 → 草稿 → 审核 → 批准生效 → 声明为记录 → 冻结 → 保留期 → 到期鉴定 → 销毁/续存 → 移交档案馆
```

系统必须能回答：**这条记录属于哪一类、应留多久、依据是什么、谁批准销毁、销毁清单在哪。**

### 3.5 四性检测（DA/T 92-2022）

| 维度 | 检测什么 | 技术手段 |
|---|---|---|
| 真实性 | 内容、结构与形成时一致 | 哈希比对、签名验证、元数据一致性 |
| 完整性 | 组件齐全、无缺失 | 归档包 manifest 校验、元数据必填项、附件计数 |
| 可用性 | 可检索、可呈现、可理解 | 格式可读性抽检、PDF/A 验证、渲染抽样 |
| 安全性 | 过程可控、存储可靠、未被非授权访问 | 权限审计、介质检测、访问日志 |

### 3.6 系统验证与变更控制

- GAMP 5 分类：本系统属于**类别 4/5**（可配置工作流 + 定制代码），不能按类别 1 处理。
- 最小交付物：URS、FS、DS、风险评估、RTM（需求追溯矩阵）、IQ/OQ/PQ、供应商评估、发布说明、缺陷与变更记录。
- 每次发版需判定"是否需要再验证"，并给出影响分析。

| 审计 | `seq` 单调、`prev_hash` 链、Merkle 日结根、HMAC 锚点、`UPDATE/DELETE` 规则置空、清理走 SECURITY DEFINER 函数、证据包导出 | Part 11 §11.10(e)；Annex 11 §9 | 锚点为对称 HMAC；无 TSA；无"变更原因"；默认留 2 年；无审阅工作流 |
| 内容完整性 | Blob 不可变 + SHA-256；版本号唯一；`effective` 唯一；保留策略不删当前版本 | §11.10(c)；Annex 11 §7.1 | 无记录声明/冻结；无 WORM；无 PDF/A |
| 外发 | 审批（发起人≠审批人）、口令、有效期、下载开关、水印、邮箱验证、来源限流、密级快照 | §11.10(d)；§11.30 | 水印是威慑，不是密码学绑定 |
| 运维 | `backup.sh`、`restore.sh`、`restore-drill.sh`、健康检查、迁移自动执行 | Annex 11 §7.2、§16 | 无定期恢复演练记录归档；无异地副本证明 |
| 追溯 | 预览水印（账号/页脚）；审计 detail；活动日志 | §11.10(e) | 无签名清单；无对外验证入口 |

**结论**：底座比多数同类产品扎实（尤其是权限与审计链），缺的恰好是"证据链的上半段"——签名、可信时间、记录生命周期、可验证性。

## 5. 差距分析

### 5.1 要求簇与差距等级

等级定义：**G1 阻断**（没有它不能宣称满足法规）；**G2 重大**（检查会开缺陷项）；**G3 一般**（改进项）。

| 编号 | 要求簇 | 现状 | 差距 | 等级 |
|---|---|---|---|---|
| R1 | 身份核验与账号唯一性 | 管理员建号，无核验记录 | 缺"入职核验证据"（依据何证件/HR 数据、核验人、时间）；缺账号不复用证明 | G2 |
| R2 | 认证强度与会话控制 | 口令 + 外部 OTP；锁定；轮换 | 内部账号无第二因子；无抗钓鱼选项；签署时无重认证；无 AAL 分级 | **G1** |
| R3 | 签名人身份与签署意愿 | 无 | 无签名身份绑定、无意愿确认、无"签署含义"选择、无签名前警示 | **G1** |
| R4 | 签名—记录绑定与签名表现 | 无 | 无密码学绑定；无签名人姓名/时间/含义的可读呈现；无防剪除设计 | **G1** |
| R5 | 签名凭证与密钥生命周期 | 无 | 无证书签发/续期/吊销/丢失处理；无 HSM/云签；无离职密钥处置 | **G1** |
| R6 | 可信时间戳 | 仅服务端时间 + HMAC 锚点 | 无 RFC 3161 TSA；锚点第三方不可独立验证；无长期验证材料 | **G1** |
| R7 | 审计追踪完整性与独立性 | 强（链 + 只追加） | 无"变更原因"；无 old/new 值摘要；无会话/认证等级字段；锚点对称 | G2 |
| R8 | 审计审阅与留存 | 可查询导出 | 无定期审阅任务与签字确认；默认 2 年 < 记录保留期；清理与记录脱钩 | **G1** |
| R9 | 访问控制与职责分离 | 强 | 无 Sign 权限位；无"签署人≠审批人≠放行人"可配规则；无记录级锁 | G2 |
| R10 | 内容完整性与防篡改 | 哈希 + 不可变 blob | 无签名；无 WORM；无副本一致性校验；无"真实副本"标识 | **G1** |
| R11 | 记录声明、保留、冻结、处置 | 无 | 无记录类别/保留期限/法务冻结/到期鉴定/销毁审批/销毁清单 | **G1** |
| R12 | 归档、长期可读与四性检测 | 无 | 无归档信息包（SIP/AIP）；无 PDF/A；无四性检测；无移交接口 | **G1** |
| R13 | 系统验证、变更控制与供应商 | 有测试与文档，无 CSV 包 | 无 URS/FS/DS/RTM/IQ/OQ/PQ；无供应商评估；无再验证判定 | **G1** |
| R14 | 业务连续性与事件管理 | 有备份/恢复脚本 | 无 RTO/RPO 定义与演练记录；无事件分级与 CAPA 闭环 | G2 |

> 统计：**10 项阻断、4 项重大、0 项一般**。阻断项集中在"签名 + 时间 + 记录生命周期 + 验证证据"四块，与第 0 节的判断一致。

### 5.2 为什么这四项是阻断级

**① 没有电子签名，Subpart C 整章不适用**
Part 11 §11.50/§11.70/§11.100/§11.200 全部围绕签名；中国法第 13 条四要件一个都答不上。现在的"审批通过"只是数据库里一个状态字段，**无法证明是谁、以什么身份、在什么时间、对哪一版内容作出的决定**。审计日志能证明"某人点了通过"，但不能证明"他确认的是这一版内容"——因为内容后来可以换成新版本。

**② HMAC 锚点只能"自证"，不能"他证"**
当前日结锚点是 `HMAC-SHA256(secret, 规范化输入)`。密钥在系统配置里，系统管理员或 DBA 可以重算整条链，让篡改后的历史"看起来仍然自洽"。对外举证时，对方会问："我凭什么相信这个 HMAC？"——答不上来。必须换成**非对称签名**（公钥可公开）加**第三方时间戳**（证明"这个摘要在该时刻已存在"）。

**③ 2 年审计保留与"记录同寿命"直接冲突**
GxP 记录常见保留 5 年、产品有效期后 1 年、或器械寿命期后 2 年。审计只留 2 年，意味着第 3 年出现争议时，**没有操作痕迹可查**。更严重的是：`audit_purge` 会按保留期删除已锚定事件，锚点还在但事件内容没了——链能验证，事实查不到。

**④ 没有验证包，功能再全也过不了供应商审计**
客户 QA 会要：URS 怎么覆盖的？风险评估做了吗？OQ 测了哪些边界？变更怎么控制？没有这套文档，客户只能自己做全套验证，成本会转嫁成"不敢买"。

### 5.3 已有能力的边界（防止过度宣称）

- **哈希链**防"悄悄改"，不防"有密钥的人重算"。加了非对称签名与外部锚定才防后者。
- **水印**是威慑与追溯线索，不是密码学绑定；截图、拍照、OCR 都能绕过。
- **版本 SHA-256** 只证明"这个 blob 的内容是这个哈希"，不证明"谁在何时确认过它"。
- **审计日志**证明"发生过某操作"，不证明"操作对应的内容没被换过"——除非签名把内容哈希一起签进去。
- **软删除 + 回收站**是可用性设计，不是合规保留；合规保留需要"禁止销毁"的强制力。

## 6. 目标方案

### 6.1 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│ 5. 验证与呈现层                                                │
│    对外验证门户 · 离线验证工具 · 验证报告 PDF · 证据包导出        │
├──────────────────────────────────────────────────────────────┤
│ 4. 记录治理层                                                  │
│    记录声明 · 保留策略 · 法务冻结 · 到期鉴定 · 销毁审批 · 归档移交 │
├──────────────────────────────────────────────────────────────┤
│ 3. 签名与证据层                                                │
│    签署流程 · 签名含义 · 签名—记录绑定 · 证据收据 · 审计锚点 v2   │
├──────────────────────────────────────────────────────────────┤
│ 2. 信任服务层（可插拔适配器）                                    │
│    CA（证书）· TSA（RFC3161）· OCSP/CRL · 可信时间源 · HSM/云签   │
├──────────────────────────────────────────────────────────────┤
│ 1. 存储与归档层                                                │
│    不可变 Blob · 对象锁 WORM · PDF/A · 归档信息包 · 异地副本       │
└──────────────────────────────────────────────────────────────┘
```

设计原则：

1. **信任服务可插拔**：私有化客户可能已有企业 CA/TSA；SaaS 客户可能要求 BYOK。适配器统一抽象，不让业务代码绑定某一家。
2. **签名与存储解耦**：签名对象是"内容哈希 + 元数据摘要"，不是文件本身。这样同一份记录可以有多个签名（编制/审核/批准），也可以在原格式与 PDF/A 之间保持同一签名语义。
3. **证据可携带**：任何一条记录都能导出"不依赖本系统即可验证"的证据包。
4. **不重写历史**：现有审计链保留，新增非对称锚点做"双锚定"过渡，90 天后停旧锚。

### 6.2 电子签名分级

| 级别 | 名称 | 技术构成 | 法律强度 | 适用场景 | 成本 |
|---|---|---|---|---|---|
| **L1** | 平台内签名 | 账号 + 第二因子 + 服务端 Ed25519 签名 + 审计绑定 | 能证明"谁在何时确认了哪版内容"，但不是法定"可靠电子签名" | 内部知悉、普通流转、非监管审批 | 低 |
| **L2** | 高级电子签名（AdES） | 第三方 CA 个人证书 + 客户端/云签 + RFC3161 时间戳 + PAdES B-T | 满足中国法第 13 条四要件与 eIDAS Art.26；可举证 | GxP 内部审批、质量文件、工程图纸 | 中 |
| **L3** | 可靠电子签名 / QES | 合格证书（QTSP/依法设立的 CA）+ QSCD/UKey/云签 HSM + PAdES B-LTA | 与手签同等效力（中国法 14 条 / eIDAS 25(2)） | 对外合同、批放行、临床知情同意、法定申报 | 高 |

**产品策略**：默认 L2，按"记录类别"配置是否强制 L3；L1 仅用于非监管场景，且界面必须明确标注"平台内签名，非可靠电子签名"。

> 这一条很重要：如果所有场景都标"电子签名"，客户会误以为已经满足 GMP；如果都不标，又显得能力不足。分级 + 明确标注，才是负责任的做法。

### 6.3 签署流程

```
选择记录/版本
  → 选择签名含义（编制 / 审核 / 批准 / 放行 / 知悉）
  → 展示将要签署的内容摘要（文件名、版本号、SHA-256 前 12 位、页数、大小）
  → 警示语（"签名具有法律效力，等同于手写签名"）
  → 重认证（口令 + 第二因子；非连续会话必须全部组件）
  → 生成签名（本地私钥 / 云签 HSM / 服务端密钥）
  → 取 RFC3161 时间戳
  → 写入签名记录 + 审计 + 证据收据
  → 返回签名清单与验证链接
```

状态机：

```
pending → authenticated → signed
        ↘ rejected（拒签，需填原因）
        ↘ expired（超时未签）
signed → superseded（记录产生新版本，旧签名保留但标记"仅对 vN 有效"）
       → revoked（仅限证书吊销/司法撤销，需双人审批 + 原因）
```

关键规则：

- **签名不可删除**，只能标记 superseded/revoked；撤销本身要留审计。
- **内容变更即新版本**：旧签名永久绑定旧版本哈希；新版本必须重新签。
- **不允许"移动签名"**：签名记录与 `version_id` 强绑定，禁止改绑。
- **批量签署**需逐条确认，不能"一次点击签 50 份"而不展示清单（Part 11 §11.200 的"每次签名用全部组件"在非连续会话下适用）。

### 6.4 签名数据模型（新增表）

| 表 | 关键字段 | 约束/说明 |
|---|---|---|
| `signature_profile` | id, tenant_id, level(L1/L2/L3), provider, cert_policy, tsa_url, requires_second_factor, allowed_meanings | 租户级签名策略 |
| `signer_identity` | user_id, legal_name, id_type, id_last4, verified_by, verified_at, evidence_ref | **身份核验记录**（Part 11 §11.100(b)） |
| `certificate_binding` | user_id, serial, issuer, subject, not_before, not_after, status, revoked_at, revoke_reason | 证书生命周期；一人可多证（换证） |
| `signature_request` | id, node_id, version_id, meaning, requested_by, assignee_id, due_at, status | 待签任务 |
| `signature` | id, request_id, node_id, version_id, content_sha256, metadata_digest, signer_id, meaning, signed_at, auth_level, cert_serial, cms_blob, tsa_token, status | **签名主体**；content_sha256 + metadata_digest 构成绑定 |
| `signature_manifestation` | signature_id, printed_name, signed_at_display, meaning_label, render_format | §11.50 的三要素呈现，随打印/导出输出 |
| `timestamp_token` | id, target_type(signature/anchor/archive), target_hash, tsa_url, token, gen_time, verified_at | RFC3161 令牌；可多条（续签） |
| `evidence_receipt` | id, node_id, version_id, bundle_hash, manifest, created_at | 单条记录的证据收据（可给第三方） |

> `metadata_digest` 覆盖：文件名、空间、密级、版本号、创建者、大小、MIME、父路径。这样"改文件名/降密级"也会使签名失效——这是很多产品漏掉的一点。

### 6.5 身份认证与账号管理增强

| 项 | 现状 | 目标 |
|---|---|---|
| 认证强度 | 口令 + 外部 OTP | 内部账号支持 TOTP / WebAuthn；管理员与签署人**强制**第二因子；AAL2 基线（抗钓鱼选项至少一种） |
| 签署重认证 | 无 | 每次签名前 step-up；非连续会话用全部组件；连续会话首次全组件、后续至少一个本人专属组件（§11.200(a)(1)） |
| 身份核验 | 无记录 | 建号时记录核验方式、核验人、时间、证据引用；离职/换证留痕 |
| 账号生命周期 | 停用/删除有校验与移交 | 增加"离职即时吊销 + 证书吊销 + 未完成签名任务转派" |
| 共享账号 | 无技术阻断 | 并发会话检测 + 设备指纹 + 异常登录告警；SOP 明令禁止（软件无法单独解决） |
| 会话 | 代数吊销、轮换 | 增加空闲超时（≤1h）与总时限（≤24h），对齐 NIST AAL2 |

### 6.6 审计追踪 v2

| 改造项 | 说明 |
|---|---|
| 非对称锚点 | 日结锚点改为 Ed25519/ECDSA 签名；公钥随证据包发布，任何人可验 |
| 外部锚定 | 每日 anchor 取一次 RFC3161 时间戳；可选再送第三方存证（司法链/可信存证平台） |
| 字段补齐 | `reason`（变更原因，Annex 11 §9 明确要求）、`old_digest`/`new_digest`、`session_id`、`auth_level`、`signature_id` |
| 保留期 | `audit_retention = max(租户配置, 该租户最长记录保留期)`；记录未销毁则审计不得清理 |
| 审阅工作流 | 按月/季度生成"审计审阅任务"，审阅人签字确认；审阅记录本身入审计 |
| 可读导出 | JSON（机器验）+ PDF（人读）+ 校验脚本；两者哈希一致 |
| 双锚过渡 | 新旧锚点并行 90 天，历史不重写；过渡期后旧 HMAC 锚仅作历史证据 |

### 6.7 记录生命周期与归档

**记录声明（declare as record）**

- 触发：审批通过、放行、归档、或手动声明。
- 动作：冻结 `(node_id, version_id)` 的内容与元数据；写入 `record_declaration`；生成证据收据；锁定编辑（只能新增版本，不能改此版本）。
- 效果：进入保留期计算；禁止删除/覆盖；可被法务冻结。

**保留策略**

| 记录类别 | 默认保留 | 起算点 | 依据 |
|---|---|---|---|
| 质量/批记录 | 产品有效期后 1 年（可配） | 放行日 | GMP |
| 临床文档 | 试验结束后 5 年（可配） | 结题日 | GCP/ICH |
| 合同 | 合同终止后 10 年 | 终止日 | 民法典/内控 |
| 普通业务文档 | 3 年 | 创建日 | 企业制度 |
| 审计日志 | ≥ 最长记录保留期 | 事件日 | Part 11 §11.10(e) |

**法务冻结（legal hold）**：一旦命中（诉讼、稽查、调查），覆盖保留期，禁止任何销毁路径；解除需双人审批并留痕。

**处置（disposition）**：到期 → 生成待鉴定清单 → 鉴定人确认 → 双人审批 → 生成销毁清单（含哈希、签名）→ 执行 → 留销毁证书。**任何一步缺失都视为未合规销毁**。

**归档信息包（AIP）**

```
AIP.zip
├── content/            原件 + PDF/A 副本
├── metadata/           XML（按 DA/T 46 或自定义 schema）
├── signatures/         CMS/PAdES 签名、证书链、TSA 令牌、DSS
├── audit/              审计摘要 + 锚点 + 证据包
├── manifest.json       文件清单 + 逐文件 SHA-256 + 包哈希
└── README.txt          校验方法（不依赖本系统）
```

### 6.8 访问控制增强（增量，不推翻现有）

- 新增 **Sign** 权限位（与 Edit/Approve 分开）：能改内容不等于能签。
- 记录级锁：声明后 `effective` 版本禁止编辑/删除；只能"发起变更 → 新版本 → 重新签"。
- 职责分离可配：签署人 ≠ 审批人 ≠ 放行人（GMP 放行场景强制）。
- 管理员边界维持现状（管配置不管内容），但补"运维访问需双人授权 + 操作录屏/会话记录"，满足 GxP 数据中心要求。
- 授权变更本身入审计（Annex 11 §12.3 已部分满足，补"授权创建/变更/取消"的独立事件类型）。

### 6.9 时间戳与长期验证

| 层 | 做法 |
|---|---|
| 时间源 | NTP 加固（多源、偏差告警）；数据库 `now()` 仅作系统时间；**对外举证一律以 TSA 时间为准** |
| 签名时间戳 | 每次签名取 RFC3161 token，嵌入 CMS（PAdES B-T） |
| 长期验证 | 签名后异步补齐证书链 + OCSP/CRL，写入 PDF DSS（B-LT） |
| 归档时间戳 | 归档包整体取 DocTimeStamp（B-LTA）；按"算法寿命/证书到期"提前续签（建议 5 年或到期前 90 天） |
| 批量优化 | 大批量归档用 RFC 4998 ERS + Merkle 树，一次时间戳覆盖多份，降低成本 |
| 验证 | 内置 ETSI EN 319 102-1 判定；对外提供离线验证工具；报告分级（Total-passed / Indeterminate / Total-failed） |

### 6.10 系统验证与证据（CSV）

| 交付物 | 内容 | 谁产出 |
|---|---|---|
| URS | 用户需求（含法规条款追溯） | 产品 + 客户 QA |
| 风险评估 | 功能关键性分级（GxP 影响） | QA + 产品 |
| FS/DS | 功能/设计规格 | 研发 |
| RTM | 需求 → 设计 → 测试 的追溯矩阵 | 研发 + QA |
| IQ/OQ/PQ | 安装/运行/性能确认脚本与报告 | 实施 + 客户 |
| 供应商评估 | 质量体系、SDLC、变更通知、缺陷管理 | 公司 QA |
| 发布验证包 | 每个版本的测试证据、变更说明、已知问题 | 研发 |
| 再验证判定 | 变更影响分析 + 回归范围 | QA |

> 产品侧能做的是"把包做成可复用资产"：客户不必从零写 URS，拿我们的模板改；每个 release 附验证包，客户引用即可。这会显著降低成交阻力。

### 6.11 对外验证门户

- 输入：证据收据 ID / 上传文件 / 扫描二维码。
- 输出：签名人（实名）、签署时间（TSA）、签名含义、证书状态、内容完整性（通过/失败）、签名级别（L1/L2/L3）。
- 两种形态：在线页（本系统）+ 离线 HTML/CLI（不依赖本系统，适合法庭/检查现场）。
- 隐私：只显示必要信息，不泄露文件内容；验证需持有文件或收据。

## 7. 分阶段迭代设计

### P0 · 可信底座（4–6 周）

**目标**：先把"证据能被别人验"这件事做成。不做签名也能产生合规价值。

| 项 | 内容 |
|---|---|
| 范围 | C01–C12 |
| 优先级 | 最高（阻断项 2、3 的一半） |
| 交付 | 迁移 `0045_audit_v2.sql`（字段 + 锚点表）、`0046_record_lifecycle.sql`（声明/保留/冻结）、`0047_signature_model.sql`（只建表不启用）、信任服务适配器、审计审阅页、记录生命周期页、保留期联动任务 |
| 验收 | ① 用公开公钥可独立验证任一日锚点；② 锚点带 TSA token 且可离线验证；③ 记录声明后，任何编辑/删除路径均被拒；④ 审计保留期 ≥ 该租户最长记录保留期；⑤ 审计事件含 reason 与 old/new 摘要 |
| 可对外宣称 | "审计链可被第三方独立验证；记录可声明、可按期保留、可法务冻结" |
| 风险 | TSA 供应商可用性与成本；老租户历史数据只能"现状锚定"，不能补签 |

**为什么先做这个**：签名是"点"，记录生命周期是"面"。没有面，签出来的东西也不知道该留多久、能不能删。

### P1 · 电子签名（6–8 周）

**目标**：让"谁、何时、以什么含义、签了哪一版内容"可签、可验、可举证。

| 项 | 内容 |
|---|---|
| 范围 | C13–C24 |
| 优先级 | 高（阻断项 1） |
| 交付 | 签署流程、含义注册表、L1 服务端签名、L2 PAdES B-T、证书管理、签名清单、待签任务、验证门户、离线验证工具、`Sign` 权限位与记录级锁 |
| 验收 | ① 签署后改 1 字节 → 验证失败；② 非连续会话第二次签名必须重新认证；③ 签名人 ≠ 审批人可强制；④ 旧版本签名在产生新版本后仍可验证，且标注"仅对 vN 有效"；⑤ 第三方用离线工具可验证 |
| 可对外宣称 | "支持 L1/L2 电子签名；L2 满足《电子签名法》第 13 条四要件与 eIDAS Art.26（依赖第三方 CA 与 TSA）" |
| 风险 | 客户端签名组件（UKey/云签）适配工作量大；证书采购与年费；用户体验（重认证）需要打磨 |

### P2 · 归档与长期保存（6–8 周）

**目标**：让记录"脱系统可读、可检测、可存 10 年以上"。

| 项 | 内容 |
|---|---|
| 范围 | C25–C31、C36 |
| 优先级 | 中高（阻断项 3 的另一半） |
| 交付 | PDF/A 转换、AIP 生成、四性检测、WORM 对象锁、异地副本、B-LT/B-LTA 续签、到期鉴定与销毁审批、移交接口、运维告警 |
| 验收 | ① 归档包在无本系统的机器上可解压、可读、可验签；② 对象锁期内任何删除请求被拒；③ 年度四性检测出报告；④ 归档时间戳续签成功且旧签名仍有效；⑤ 销毁全流程留痕并出销毁证书 |
| 可对外宣称 | "支持电子档案单套管理的技术与四性检测要求（需配合组织制度与三员管理）" |
| 风险 | WORM 存储成本；PDF/A 转换对复杂版式（CAD、大表格）的保真度；续签任务的长期运维 |

### P3 · 验证与认证（8–12 周，持续）

**目标**：让客户 QA 拿得走一套包，直接引用；让产品能进受监管采购清单。

| 项 | 内容 |
|---|---|
| 范围 | C32–C35，外加渗透测试、等保/SOC 2 |
| 优先级 | 中（决定"能不能卖进大客户"，不影响单点功能） |
| 交付 | URS/FS/DS/RTM 模板、IQ/OQ/PQ 脚本、供应商评估包、变更控制流程、再验证判定表、BCP 与演练记录、渗透测试报告 |
| 验收 | ① 客户 QA 用我们的包在 2 周内完成供应商评估；② 每个 release 附验证包与变更说明；③ 第三方审计可追溯每条需求到测试用例 |
| 可对外宣称 | "提供可复用的计算机化系统验证包（GAMP 5 类别 4/5）" |
| 风险 | 文档工作量大且需专人维护；一旦承诺就必须每个版本更新，否则比没有更糟 |

### 依赖关系

```
P0 ──> P1 ──> P2
 │      │
 └──────┴────> P3（可与 P2 并行启动文档部分）
```

P1 依赖 P0 的签名数据模型与重认证；P2 依赖 P1 的签名与 P0 的保留策略；P3 可以在 P1 结束后就开始写 URS/RTM，不必等 P2。

## 8. 关键设计决策与取舍

| 编号 | 决策 | 选择 | 理由 | 代价 |
|---|---|---|---|---|
| D1 | 自建 CA/TSA 还是第三方 | **第三方为主**，自建仅测试环境 | 法律效力依赖信任链与资质；自建 TSA 对外不被认可 | 年费、依赖外部可用性 |
| D2 | 服务端签名还是客户端签名 | **L1 服务端，L2/L3 客户端或云签** | QES 要求签名制作数据由签名人单独控制；服务端代签无法满足 | 客户端适配复杂 |
| D3 | HMAC 锚点如何迁移 | **双锚定 90 天**，历史不重写 | 重写历史会破坏已有证据；双锚可平滑过渡 | 短期存储与计算翻倍 |
| D4 | WORM 用什么实现 | **对象存储 Object Lock（Compliance 模式）** | 数据库层做不到真正不可删；对象锁有法律认可度 | 成本、运维复杂度 |
| D5 | 审计保留期怎么定 | **按记录类别取最大值**，不设全局统一值 | 统一 2 年会与 GxP 冲突；统一 10 年成本过高 | 配置复杂，需要租户管理员理解 |
| D6 | 是否把原件转 PDF/A | **双套：原件 + PDF/A 副本** | 转换可能丢版式/公式；原件才是"原始记录" | 存储翻倍 |
| D7 | 多租户 TSA 配额 | **平台级共享 + 租户计量** | 单租户独立采购不现实；计量便于成本分摊 | 需要配额与限流设计 |
| D8 | 签名私钥是否托管 | **绝不托管**（仅托管加密密钥） | 托管即失去不可否认性 | 密钥丢失=永久无法签名，需恢复流程 |
| D9 | 是否支持"补签"历史文件 | **不支持补签，只支持"现状声明"** | 补签是伪造时间，检查员一眼看穿 | 老客户迁移需解释 |
| D10 | L1 是否也叫"电子签名" | **叫，但必须标注"平台内签名"** | 避免误导；也避免能力被低估 | 文案与 UI 需严格区分 |

## 9. 风险与合规边界

### 9.1 软件不能替代的部分

必须由客户组织承担，产品只能提供模板与证据位：

- SOP 体系（账号管理、审计审阅、备份恢复、变更控制、销毁）；
- 培训记录与人员资质（Part 11 §11.10(i)）；
- 系统清单与定期评估（Annex 11 §4、§11）；
- 供应商审计与质量协议；
- 偏差、事件、CAPA 闭环；
- 数据治理责任（谁对数据完整性负责）。

**这一条要写进商务话术**：任何"买了就合规"的承诺都是不负责任的。

### 9.2 主要风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| TSA/CA 服务不可用 | 签署失败、业务中断 | 双 TSA 供应商、异步重试、降级为 L1 并标注 |
| 跨境数据与信任服务 | 境内客户使用境外 TSA 的合规争议 | 优先境内依法设立的 CA/TSA；境外场景单独配置 |
| 密钥/证书丢失 | 无法签名或无法解密 | 双证书、恢复流程、加密密钥托管（签名密钥不托管） |
| 性能 | 签署与验证引入延迟 | 签名同步、时间戳与 LTV 异步补齐 |
| 历史数据 | 老文件无签名、无保留策略 | 只做"现状锚定 + 声明"，不补签 |
| 成本 | TSA 调用、WORM、证书、验证人力 | 分级签名、批量 ERS、按记录类别设置保留期 |
| 过度承诺 | 销售宣称"符合 Part 11"引发审计失败 | 统一话术：分级 + 边界 + 需客户配合项 |

### 9.3 法律意见

中国法下"可靠电子签名"的认定、跨境场景的效力、以及特定行业（如人类遗传资源、涉密档案）的额外限制，需由律师与行业顾问出具意见。本文只做技术映射。

## 10. 待确认事项（需要拍板）

1. **目标行业优先级**：医药 GMP / 医疗器械 / 临床研究 / 通用合同，哪个先做？这决定 L2 与 L3 的比例，以及是否需要 GCP 专属流程。
2. **信任服务选型**：是否接受第三方 CA/TSA？境内优先还是允许境外？预算区间？
3. **部署形态**：SaaS 客户是否允许 BYO CA/TSA（自带证书与时间戳）？私有化客户是否要求完全离线（离线场景只能用本地 TSA + 定期外部锚定）？
4. **默认保留期**：质量记录、合同、普通文档分别定几年？是否需要按客户行业预置模板？
5. **是否出海**：是否需要 eIDAS/QES 与 EU Trusted List 互认？如果需要，L3 的供应商选择会不同。
6. **是否接受"分阶段宣称合规"**：P0 后只宣称"审计可独立验证"，P1 后才宣称"支持电子签名"，避免一次性大话。
